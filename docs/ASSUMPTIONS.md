# ECHOES OF THE VOID — conflicts between the specification documents, and the decisions taken

Written by the compliance auditor (task 6df4d703) on 2026-11-03. Sources:
- **MPRD**: the original Master PRD (ECHOES_OF_THE_VOID_Master_PRD.docx)
- **RM**: the Post-PRD Technical Development & Production Roadmap
- **D3**: Implementation PRD, Document 03
- **STORY**: Gameplay & Story Integration PRD
- **BLEND**: Blender 3D Asset Production PRD
- **GODOT**: Godot 4 Game Development PRD

Rule used: where documents disagree, **follow the most specific document for that subject**:
- STORY for missions, puzzles, save content and the ending;
- BLEND for assets;
- GODOT/D3 for engine structure.

A conflict with what is actually built is resolved by mapping, not by re-building, when the built version already meets the intent and is covered by tests (RM §3 "Do not overwrite working systems without checking dependencies"; D3 "Preserve working features").

| # | Topic | What the documents say | Decision | Why |
|---|---|---|---|---|
| 1 | Engine | MPRD: Unreal Engine 5, Blueprint-first. RM, D3, STORY, BLEND, GODOT: Godot 4.x, GDScript. | **Godot 4.7.2** with GDScript (version recorded in project.godot `config/features` and README). | All five later documents agree. UE5 also cannot be built or packaged on this machine (no GPU, GUI-only editor). |
| 2 | Platforms | MPRD: "Windows PC first; Android adaptation after the PC demo". RM, D3, STORY, BLEND, GODOT: Windows PC (Windows-first). GODOT §11: "Avoid … Android porting in this release". **Sonujeet plays on an Android phone (realme P3, 1600×720)** and asked for big touch buttons after THE DEEP. | **Windows is the acceptance platform**: every DoD item is judged on Windows. **Android (APK) and Web builds ship as extras** with touch controls and the Mobile/Compatibility renderers. | Android support is already built and tested (touch UI 1.35×, mobile quality preset), so no Windows work is held back by it. GODOT §11's concern is schedule risk, not a ban. MPRD and Sonujeet's own device ask for Android. |
| 3 | Renderer | RM: "based on hardware capabilities". GODOT: Forward+ first, Compatibility only if testing requires it. | Forward+ on desktop; the Mobile renderer on Android; Compatibility for the web (project.godot `rendering_method`, `.mobile`, `.web`). | Satisfies both: Forward+ is the PC renderer, and the others are used only where the platform requires them. |
| 4 | Visual target | RM, D3: "Realistic Cinematic AAA-Inspired". GODOT §2: "cinematic indie quality, not a guarantee of AAA production values". BLEND §1: "not film-quality assets for every object". | Cinematic indie quality: lighting, fog, composition, sound and timing first; realism passes on the hero assets (astronaut, shuttle) now. | GODOT and BLEND are the specific production documents. "AAA-inspired" is read as a direction, not a bar. |
| 5 | Folder structure | RM §1.2, GODOT §4 and BLEND §4 each propose a **different** tree (e.g. `resources/` vs `data/`, `scripts/quests` vs `scripts/missions`, `save_system` vs `save`, `EOV_Blender/…`). | Keep the existing layout; **docs/FOLDER_MAPPING.md** maps every proposed folder to where it lives. The Blender sources go to `blender_src/` outside `res://`. | The three trees conflict with each other. Moving folders would break every `res://` path and the import cache for no player gain (RM §3). |
| 6 | Scene / node architecture | D3 Phase 2 and GODOT §5: `Player.tscn` with VisualRoot/CameraPivot/SpringArm3D/Camera3D/InteractionArea/WeaponSocket; also LevelRoot, WeaponBase, EnemyBase, InteractableBase, HUD, PauseMenu and Inventory `.tscn`; D3 also names Main.tscn, MainMenu.tscn, TestEnvironment.tscn and cryo_chamber.tscn. | The nodes are built in code (one boot scene, `scenes/main.tscn`). Equivalents: CharacterBody3D `Player` (scripts/player/player.gd); the node names VisualRoot and CameraPivot → SpringArm3D → Camera3D match D3 since commit f0d52bc (player.gd:_ready, player_controller.gd:setup); InteractionArea = InteractionComponent (proximity + view test, which GODOT §6 allows as "raycast or Area3D"); WeaponSocket = BoneAttachment3D on bone `prop.R`. The lead adds thin `.tscn` wrappers under the names the documents use. | Code-built scenes stay diffable and are covered by the autotest. The wrappers satisfy the named-file requirement without a second implementation. |
| 7 | Script names | D3 Phase 3/5: player_controller, player_camera, player_animation, player_interaction; combat/weapon_base, weapon_manager, damage_system, health_component. | player_controller.gd = input + camera; player_anim.gd = animation; components/interaction_component.gd = interaction; weapons/weapon_base.gd; components/combat_component.gd = weapon manager; damage = weapon_base `_apply_hit` → HealthComponent `take_damage` (components/health_component.gd). | Same responsibilities, already split one per script (GODOT §9 "one responsibility per major script"). |
| 8 | Main scene | GODOT Phase 1: "Main scene opens TestEnvironment". D3 Task 001: Main.tscn + TestEnvironment.tscn. A shipping game must start at its menu. | `main.tscn` boots to the main menu. `scenes/test_environment.tscn` (floor, sun, sky, 6 blocks, the player) is its own scene and can be run directly (`godot --path . res://scenes/test_environment.tscn`). STORY Phase 1's "system test scene" (player + terminal + door + pickup + enemy) would extend it; see the audit. | D3/GODOT describe the first day of a project. The shipped build must open on the menu (RM Phase 9). |
| 9 | Mission titles | MPRD: Awakening / Dead Signal / The Experiment / Last Transmission. RM and D3: Awakening / Lost Research / Containment Failure / Final Extraction. STORY: M01 Awakening / M02 Lost Research / M03 Containment Failure / **M04 Core and Extraction**. | Titles: 01 AWAKENING, 02 LOST RESEARCH, 03 CONTAINMENT FAILURE, 04 FINAL EXTRACTION (data/missions.tres). Codes M01–M04 are the STORY ids. The internal ids (awakening, dead_signal, experiment, last_transmission) are kept because saves use them. | Two documents (RM, D3) against one name M04 "Final Extraction". The internal ids are mapped, not renamed, so existing saves stay valid. |
| 10 | Mission boundaries | STORY: M02 ends when "research access credential acquired and security route unlocked"; M03 = Security Sector to the reactor route; M04 = reactor puzzle + exterior + extraction. RM: M03 "restore security **and reactor** systems". MPRD: M02 = restore communications. | Built: M01 cryo (wake, door, pistol, first Stalker, generator puzzle). M02 research + security (Iyer's data, code 0417, rifle, Brute, comms). M03 reactor (lab, conduit puzzle, survival). M04 exterior + extraction (transmission, Herald, shuttle). | Every beat STORY lists is present, in the same order. Only where one mission ends and the next begins differs. This split matches RM ("security and reactor" in Containment Failure) and keeps the MPRD comms beat. Moving the reactor into M04 would make M04 three areas long and M03 thin. |
| 11 | Puzzles | RM/D3: power restoration, security access/terminal, reactor stabilisation. STORY: PZ01 Power Routing (Cryo, "sequence of power nodes"), PZ02 Access Alignment (Research/Security, clues found nearby), PZ03 Reactor Stabilization ("multi-step sequence under pressure"). | PZ01 = generator start order B→C→A in the cryo generator room (clue in Wren's note; a wrong order trips and resets). PZ02 = security override keypad 0417 from two logs (Okoye's + Iyer's). PZ03 = conduit-rotation board in the reactor, followed by the timed survival defence. | Each matches its STORY rule and location. PZ03's "under pressure" comes from the alarm, the enemy waves and the survival timer that follows, not from a timer on the board itself, so a phone player is never failed by touch precision. |
| 12 | Enemy placement | STORY: Security = Sentinel encounter; Reactor = "Brute/boss escalation". | Sentinels in Security; the first Brute in Security's vehicle bay; Brute + Stalkers + Sentinel waves in the Reactor survival; the Herald boss in Extraction. | Escalation is kept. The earlier Brute gives a readable 1-on-1 introduction before the mixed reactor waves. |
| 13 | Jump / crouch | RM/D3 require jumping and crouching. GODOT §6: "jump if level design needs it"; prone is out of scope. | Jump and crouch are implemented and used by the level (a crouch beam and a jump gap in the cryo tutorial). No prone. | Satisfies all three. |
| 14 | Inventory | RM/D3: resources, key items, mission objects, inventory interface. GODOT: "small item list; capacity only if required". | Weapons, ammo reserves (cap 96/192), medkits (cap 3), keycards and research logs. The screen is in the Journal ("Inventory & logs"). | Small list, caps only where balance needs them. |
| 15 | Save content | STORY §11: checkpoint, **completed mission IDs**, objective flags, key items, ending-complete flag, schema version, safe defaults; do not save transient enemies/VFX. RM/D3: player progress, inventory, unlocked areas, checkpoint, settings. | Save = {version, game_version, mission index + objective index, area, checkpoint, flags, player (hp, weapons, ammo, medkits, keycards), logs, stats}. Completed missions = all indices below `mission`. Unlocked areas/doors and dead enemies are flags. The ending sets `game.complete`. Settings are in their own file (user://echoes_settings.cfg). Missing keys get defaults on load (game.gd `load_game` merge). | Equivalent information without a redundant list. Settings are kept separate so a save reset never wipes the player's controls. |
| 16 | Asset naming | BLEND §5: CHR_Astronaut_Body, ENV_CryoWall_A, PROP_Terminal_A, WPN_PulseRifle, MAT_PaintedMetal. | Files keep short lowercase names (`astronaut.glb`, `env/cryo_pod.glb`), and the register uses the PRD-style IDs (docs/ASSET_REGISTER.md). Material slots are named by role (Panel, Trim, Hazard, Emit*, Glass*). | Code loads assets by file name. Renaming 83 files and their imports adds risk for no player gain. The register is where BLEND asks for the IDs. |
| 17 | Blender source files | BLEND §5/§11 and RM: keep source `.blend` for every critical asset. | Characters, creatures, weapons and figures have `.blend` files. The environment kit (73 files) is **generated by Python scripts** that rebuild every file, so the scripts are its source. All sources are copied into `blender_src/` for the source zip. | A procedural source is a stronger source than a hand-edited `.blend`, because it is reproducible. Noted as a deviation, not hidden. |
| 18 | Alien colour | BLEND §2: "restrained alien green/cyan". MPRD/DESIGN: violet twilight world, violet Echo crystal. | Violet crystal for the organism; cyan for station tech and UI; teal for the bioluminescent plants. | The original design defines the organism's look, and it is already in every area. BLEND's palette line is advisory and is still met for the plants. |
| 19 | Testing method | RM/D3 assume play-testing in the editor and on "your actual PC". STORY §12: 4 of 5 first-time testers. | Automated headless tests (autotest, collide, balance, ai_test, Windows exe under wine) give the evidence. Human-tester criteria and the "60 FPS on your PC" measurement are marked **open — needs Sonujeet** in the audit, and an in-game FPS readout lets him measure. | This machine has no GPU and no testers. The audit never marks a human-only check as passed. |
| 20 | Schedule / process | RM/D3: 10–12 weeks, one feature at a time, "do not skip milestones". | The milestones M1–M11 are audited for their result, not their calendar. Each system has a test. | The documents' purpose is quality gates, and the audit checks every gate with evidence. |
| 21 | Weapon readability | BLEND §3: "clear first-person/third-person readability". | Third-person only (over the shoulder). Weapons attach to `prop.R`, and character key/rim lights keep them readable. | The game has no first-person mode (MPRD: third-person). |
| 22 | Level streaming | GODOT Phase 7: streaming only if profiling needs it. | Controlled scene transitions between the 6 areas (GameMode.load_area), with a checkpoint saved at each. | As specified. |
